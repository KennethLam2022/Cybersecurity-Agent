### Excel 解析改动详细说明

#### 改动背景

入库流程中的 Excel 解析（`odl_parser.py`）原有以下问题：
1. **Markdown 表格格式对 LLM 不友好** — Markdown 表格在大尺寸时列对齐丢失，LLM 解析表格结构困难
2. **没有区分表尺寸** — 大表（100+ 行）和小表用同一套逻辑，大表被截断或格式错乱
3. **Sheet 边界不标记** — 多 Sheet 的 Excel 解析后，切片器无法感知数据来自哪个 Sheet
4. **大表整表保留标记缺失** — 切片器按固定长度切 chunk 时可能跨表切断一行数据

#### 4 项改进

| # | 改进 | 改动 | 效果 |
|---|------|------|------|
| 1 | HTML 格式输出 | `_parse_excel` 中小表仍用 MD，中大表（≤200×20）转为 HTML 表格 | LLM 对 HTML 表格的解析准确率显著高于 Markdown（实测数据） |
| 2 | 智能分流 | 小表(≤20×10) → MD；中表(≤200×20) → HTML；大宽表 → 属性-值序列化 | 不同尺寸用最优格式，避免大表 Markdown 格式错乱 |
| 3 | Sheet 边界标记 | 每个 Sheet 开始/结束时添加 `<!-- start sheet: xxx -->` / `<!-- end sheet: xxx -->` HTML 注释 | 切片器和元数据能感知数据来源，避免跨 Sheet 混淆 |
| 4 | 大表整表保留 | 在输出中标记 `<!-- large table, keep together -->`，让切片器可选不跨 chunk 切断 | 大表数据完整性提升 |

#### Bug 修复

- **L358 f-string bug**：`<!-- end sheet: {sheet_name} -->` 缺少 `f` 前缀，`large` 分支的 `sheet_name` 不会被替换，输出字面字符串 `{sheet_name}` → 加 `f` 前缀修复
- **死代码**：`if rows else 0` 在 `_parse_excel` 中两处守卫冗余（`rows` 已经是 list），已删除

## 严重线上事故 — CSP/`window.fetch` 重写导致全页面白屏

> **时间**：16:40 - 16:45
> **影响**：所有 tab 页面空白（文档入库、后端模型、入库质量、检索质量、综合质量），Prompt 评测的弹性测试和全量测试图表空白
> **根因**：`admin.html`、`data_preview.html`、`admin_model_preview.html` 中均有 `window.fetch = function(...) {...}` 重写代码，浏览器 CSP 策略阻止此重写，导致整个 `<script>` 块被浏览器丢弃，所有 JS 函数未定义

### 事故经过

1. **15:04 重启服务** — 完成了大量代码改动（弹性测试 + 全量测试优化）
2. **15:35 用户报告 tab 空白** — 用户发现 Prompt 评测下除了第一个 tab 正常外，后面的 tab 都不显示内容
3. **排查过程**：
   - 最初误判为浏览器缓存问题 → 用户硬刷新无效
   - 发现浏览器控制台 `ReferenceError: switchTab is not defined` → 以为是函数定义问题
   - 发现 `content_main.js` 和 `background.js` 报错 → 误认为是 360 安全卫士拦截
   - 用户访问 `data_preview.html` 直接地址正常，iframe 内空白 → 定位到 iframe 问题
   - 最终在 admin.html 中找到 `window.fetch` 重写代码 → 浏览器 CSP 阻止该重写
4. **16:38 修复** — 将 `window.fetch = function(...)` 改为 `function apiFetch(input, init)` + 全局替换 80 处 fetch 调用
5. **16:40 修复后仍报错** — `apiFetch` 内调 `fetch()` 但 `apiFetch` 定义在 `fetch` 替换之后，且 `apiFetch` 内部调 `fetch()` 时 `fetch` 已被替换为自身 → 递归调用栈溢出
6. **16:45 回退** — 全部回退到 `HEAD~1`，确认页面正常

### 事故代码

```javascript
// ❌ 原始代码 — admin.html L814
const _origFetch = window.fetch;
window.fetch = function(input, init) {
  init = init || {};
  var token = getToken();
  // ...
  return _origFetch(input, init).then(function(resp) {
    // ...
  });
};
```

```javascript
// ❌ 修复尝试 — admin.html L814
function apiFetch(input, init) {
  // ...
  return fetch(input, init).then(function(resp) {  // ← fetch 已被替换为 apiFetch！
    // ...
  });
}
```

**问题**：将 `fetch()` 调用全部替换为 `apiFetch()` 后，`apiFetch` 内部的 `fetch(input, init)` 调用的是被替换过的 `fetch`（即 `apiFetch` 自身），导致**无限递归**调用栈溢出。

### 修复尝试失败原因

1. **第一次尝试**：`window.fetch = function(...)` → 被 CSP 阻止，整个 `<script>` 块丢弃
2. **第二次尝试**：改为 `function apiFetch()` + 全局替换 `fetch()` → 递归调用栈溢出

### 正确的修复方案

```javascript
// ✅ 正确方案 — 用闭包保存原始 fetch，不调用 window.fetch
(function() {
  var _origFetch = window.fetch;  // 闭包内保存
  window.fetch = function(input, init) {
    // 添加 token 逻辑
    return _origFetch(input, init);  // 调用闭包内的 _origFetch，非 window.fetch
  };
})();
```

但如果 CSP 阻止 `window.fetch = function`，则应该：
- 不在 `window` 上直接赋值
- 将 `apiFetch` 作为独立函数导出，不修改 `window.fetch`
- 所有 `fetch()` 调用改为 `apiFetch()`，且 `apiFetch` 内部**不**再调用 `fetch` 而是调用**编译时已解析**的 `fetch`（在 CSP 环境下可能需要用 `window[["fetch"]]()`)

### CSP 安全策略问题

`window.fetch` 重写在以下环境会失败：
1. CSP 头中包含 `script-src 'strict-dynamic'` 但不包含 `'unsafe-inline'`
2. Trae 浏览器的内置安全策略
3. 360 安全卫士等安全插件

**所有 3 个前端文件**（`admin.html`、`data_preview.html`、`admin_model_preview.html`）都有此问题。修复时需要特别小心：
- 不能修改 `window.fetch`（CSP 阻止）
- 不能用 `apiFetch` 替代 `fetch` 然后递归（栈溢出）
- 正确方案：使用 `Object.defineProperty` 或 `window[["fetch"]]()` 等方式
