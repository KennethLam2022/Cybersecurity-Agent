## 二、实现历程

### 阶段一：文档解析与清洗（2026-05-23）

**目标**：将 344 份源文档（去重后）解析为结构化 Markdown

**技术选型**：
- 文本型 PDF → OpenDataLoader
- 扫描件 PDF → pypdfium2 + RapidOCR
- .docx → python-docx
- .doc（旧版 Word）→ pywin32 + Word COM 转换为 .docx

**踩坑记录**：

| 问题 | 原因 | 解决 |
|------|------|------|
| .doc 格式 python-docx 无法解析 | python-docx 只支持 .docx | 添加 `_convert_doc_to_docx()` 用 pywin32 自动转换 |
| 某份 .doc 转换卡死 | Word COM 处理大文件卡住 | 用户手动在同一目录下转成 .docx 后重新跑 |
| 1份文件加密无法读取 | PDF 有打开密码保护 | 检测到加密后跳过并记录日志 |
| 1份45MB超大PDF跳过 | 文件过大，ODL解析超时 | 记录到跳过清单，后续可单独处理 |
| LLM清洗时 API Key 传递问题 | 多次切换 dotenv/env 方式 | 统一用系统环境变量 `SILICONFLOW_API_KEY` |
| 文档范围反复确认 | 对话上下文丢失导致重复沟通 | 记录到系统记忆："文档范围已第三次沟通确定，不要再讨论" |

**范围变更记录**：
```
初始范围: 344份 → 排除NIST/美国标准
         → 仅保留通信行业(YD标准)
         → 排除中国移动子目录/隐私计算/旧版YD1732-1748系列
         → 补充欧盟GDPR
         → 去重按最新文件保留
最终确定: 前4类(国家法律/等保国标/CII关基/通信行业) = 117份
        批次3-6(数据安全/网络安全体系/APP安全/基线标准/漏洞管理) 挂起
```

**产出物**：
- 117份结构化 Markdown（`MD_Cleaned/`）
- 阶段一_文档处理清单.xlsx（文件名、路径、大小、提取方式等）

### 阶段二：切片与向量化入库（2026-05-24）

**目标**：将 MD 文件切片 → embedding → 写入向量库

**切片策略**：
```
按 ##/### 标题分割 → 父文档 section
  └─ 超过 256 字再切子 chunk
  └─ chunk_size=256, chunk_overlap=25
  └─ Chunk ID: {文件名}__s{节索引}__{子索引}
  └─ Parent ID: {文件名}__s{节索引}（支持父文档检索）
```

**向量化方案**：
- Embedding: Ollama `quentinz/bge-small-zh-v1.5`（512 token 窗口）
- Chroma: `chromadb.PersistentClient` 直接管理
- FAISS: LangChain FAISS，短路径 `%TEMP%/cyber_faiss`

**分批策略**：20份/批，6批次，用时间换空间

**踩坑记录**：

| # | 问题 | 现象 | 根因 | 解决 |
|---|------|------|------|------|
| 1 | **Chunk ID 重复** | `DuplicateIDError` | 同名章节（多个"前言"、"关键条款"）标题重复 | 改为 `{stem}__s{枚举索引}__{i}` |
| 2 | **Embedding 输入超长** | "input length exceeds context length" | bge-small-zh-v1.5 仅 512 token | chunk_size 从 1500→500→300→256 逐步降 |
| 3 | **Chroma HNSW compaction bug** | 写入成功(exit 0)，重读时报 `InternalError` | ChromaDB 1.5.9 Rust HNSW compactor 异步损坏索引 | ① 全量重建策略 ② 最终设 `sync_threshold=100000` 绕过 |
| 4 | **FAISS 中文路径** | `save_local` 报错 "could not open for writing" | Windows 中文路径问题 | 改用纯 ASCII 短路径 `%TEMP%/cyber_faiss` |
| 5 | **Chroma 全量重建 vs FAISS 增量** | embedding 重复计算，每批多花 ~20s | 两者独立 embed | 后来用 `verify_chroma_workaround.py` 从 FAISS 逆向提取向量 |
| 6 | **OpenAI SDK 调用 Reranker** | `TypeError: got unexpected keyword argument 'json'` | OpenAI SDK `post()` 参数不兼容 | 改用 `requests.post()` 直接调用 |
| 7 | **Ollama embedding CPU 慢** | 7316 chunks 耗时 ~20min | CPU 推理 | 从 FAISS 逆向提取向量跳过二次 embedding |

## 四、关键技术决策

### 4.1 放弃 Chroma → 双库回归

**问题**：ChromaDB 1.5.9 Rust HNSW compactor 在 C/S 模式下，当 `total_items ≥ sync_threshold` 时，compactor 运行一次就永久损坏索引。

**根因**：#7090 确认 — Rust compactor 写 `index_metadata.pickle` 时存在 float/int 序列化不匹配（`length.bin` 头 4 字节应写入 u32，实际写成了 IEEE 754 的 1.0）。

**解决**：设置 `hnsw:sync_threshold=100000`（大于总嵌入数），compactor 永不运行，数据全在 WAL 中，重启时从 WAL 重建 HNSW。代价是 WAL 存两份（~15MB），但对当前数据量完全可接受。

### 4.2 FAISS 路径问题

Windows 中文路径导致 FAISS `save_local` 报错。改用 `%TEMP%/cyber_faiss` 纯 ASCII 短路径解决。

### 4.3 Reranker API 选型

对比三种方案：
- **本地 GPU**：没有显卡 ❌
- **Ollama 绕行**：没有原生 rerank API，效率低 ❌
- **硅基流动 API**：已有 Key、免费额度、原生 rerank 接口 ✅

### 4.4 LangChain 架构

虽然在索引构建过程中被多次修改绕开（Chroma 改用 PersistentClient 直接管理），但整体仍基于 LangChain 的 FAISS wrapper 和 OllamaEmbeddings，为后续 Agent 对接保留了兼容性。
