# RAG 文档处理流程重构设计

## 背景

现有 RAG 文档处理流程中，**重名检测**位于文件提取之后，且后端代码仅在扫描阶段静默去重（同名保留最新），不给用户选择权。导致两个问题：

1. **资源浪费**：提取（ODL/Ocr/RapidOCR）+ LLM 清洗消耗大量时间和 Token，如果之后才发现冲突，前面的计算就白费了。
2. **缺乏用户控制**：用户无法决定冲突文件的处理方式（覆盖/跳过/重命名），也无法在批量处理前筛选范围。

## 新流程

```
阶段一（扫描确认期）                          阶段二（处理执行期）
┌─────────────────────────┐   用户确认后     ┌─────────────────────────┐
│ ① 文件扫描+重名校验    │ ──────────────→ │ ③ 文件提取 (OdlParser) │
│ ② 用户确认范围         │                  │ ④ 数据清洗 (LLM)       │
│   · 勾选文件            │                  │ ⑤ LLM 切片             │
│   · 解决重名冲突        │                  │ ⑥ 向量化入库           │
│   · 点击"开始处理"      │                  └─────────────────────────┘
└─────────────────────────┘
```

**优势**：用户在提取之前就决策，0 Token 浪费。

## 状态机

```
                ┌──────────┐
                │ scanning │ 拖入文件
                └────┬─────┘
                     ↓
               ┌───────────┐
               │ duplicate │ 检测到重名 → 用户决策
               └─────┬─────┘
                     ↓ 用户解决了所有冲突
               ┌───────────┐
               │  pending  │ 等待用户点击"开始处理"
               └─────┬─────┘
                     ↓ 用户确认
               ┌───────────┐
               │  queued   │ 排队等待
               └─────┬─────┘
                     ↓
              ┌─────────────┐
              │ extracting  │ ODL/Ocr 解析
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │  cleaning   │ LLM 清洗
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │  chunking   │ 语义切片
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │ embedding   │ 向量化入库
              └──────┬──────┘
                     ↓
              ┌─────────────┐
              │    done     │ ✅
              └─────────────┘

  error ← 任意步骤可失败至此
```

共 **10 种状态**，比原来 8 种多 `scanning` 和 `pending`。

## data_preview.html 改动要点

### 1. 处理流程图（flow-section）

从 5 步改为 6 步：

```
① 文件扫描+重名校验 → ② 用户确认范围 → ③ 文件提取 → ④ 数据清洗 → ⑤ LLM 切片 → ⑥ 向量化入库
```

第②步用不同颜色高亮（绿色/紫色），强调用户介入点。

### 2. 状态标签（status-badge）

新增的 CSS 类：

| 状态 | CSS class | 颜色 | 动画 |
|------|-----------|------|------|
| `scanning` | `status-badge scanning` | 蓝色 dot | pulse |
| `duplicate` | `status-badge duplicate` | 橙色 dot | 无 |
| `pending` | `status-badge pending` | 灰色 dot | 无 |

已有状态保留不变：`queued` / `extracting` / `cleaning` / `chunking` / `embedding` / `done` / `error`

### 3. 文件行结构

每行增加左侧 checkbox（阶段一启用，阶段二禁用）：

```
[☑] [PDF] 等保2.0-通用安全要求.pdf  4.2 MB  ⚠️ 重名冲突  [覆盖 ▼] [✕]
[☐] [DOC] 数据安全管理办法.docx     1.8 MB  ⏸ 待确认    [✕]
```

重名冲突行的操作下拉提供三个选项：
- **覆盖旧版** — 用新文件替换旧文件
- **跳过此文件** — 保留旧版，不处理新版
- **全部保留** — 自动重命名（追加 `_v2` 后缀）

### 4. 操作栏变化

**阶段一（确认期）：**
```
[☐ 全选] [⚡ 批量: 覆盖 ▼]  |  [▶ 开始处理 (N个文件)]  [🗑 清空全部]
```

- "开始处理"按钮默认禁用，仅当勾选了文件且所有重名冲突已解决时才亮起
- 显示选中文件数

**阶段二（执行期）：**
```
[⟳ 处理中 (N/M)] [⏹ 停止] [🗑 清空全部]
```

与现有保持一致。

### 5. 拖拽后的交互流程

```
用户拖入文件
  ↓
自动触发扫描（scanning 状态闪烁 1-2 秒模拟）
  ↓
文件进入列表，状态为 pending 或 duplicate
  ↓
用户勾选文件 + 解决重名冲突
  ↓
点击"开始处理"
  ↓
进入阶段二，逐批次执行
```

### 6. 汇总栏同步更新

新增维度：

| 旧 | 新 |
|----|----|
| 文档总数 / 成功 / 失败 / 处理中 | 文档总数 / ✅成功 / ❌失败 / ⏳处理中 / ⚠️重名 / ⏸待确认 |

## 与后端 API 的对接约定（设计约定，暂不实现）

后续后端 API 需提供以下端点：

```
POST /api/scan          输入: 文件路径列表  输出: 扫描结果(文件名/大小/哈希/重名标志)
POST /api/resolve-conflict  输入: {file, action: "overwrite"|"skip"|"rename"}  输出: 更新后的列表
POST /api/start-processing  输入: 文件路径列表  输出: 任务ID
GET  /api/status/{taskId}  输出: 每个文件的当前状态
```
