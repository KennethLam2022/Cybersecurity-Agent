## 1. 项目概述

构建一个面向移动运营商网络安全管理领域的智能问答 Agent，基于知识库（信息安全标准/法规/行业规范）提供合规标准查询、等保要求解答等专业问答服务。

### 1.1 项目目标

| 维度 | 目标 |
|------|------|
| 核心能力 | 标准/合规问答（能查标准、查合规要求、查等保测评要点） |
| 第一版形式 | 全屏对话界面 + HTML 富文本渲染 |
| 后续扩展 | Qwen Agent 架构、Flowise 低代码架构、全界面版（配置面板+知识库管理） |
| 交付要求 | 美观专业，可直接展示成果 |

### 1.2 三阶段架构规划

| 阶段 | 架构 | 状态 |
|------|------|------|
| 第一版 | LangChain（TypeScript） | 本次实现 |
| 第二版 | Qwen Agent（通义系列） | 后续 |
| 第三版 | Flowise（低代码可视化） | 后续 |

## 4. 知识库预处理管道（Docling + LLM 清洗）

### 4.1 管道流程

```
原始文件（PDF/DOC/DOCX）
    │
    ▼
┌──────────────────────────────────────────────────┐
│  阶段一：文档解析（三引擎自动切换）                │
│  ├─ DOCX       → python-docx     (0.2s/份)       │
│  ├─ 文本型PDF  → OpenDataLoader  (0.5-4s/份)     │
│  └─ 扫描件PDF  → pypdfium2+RapidOCR (~6s/页)     │
└──────────────────┬───────────────────────────────┘
                   ▼
┌─────────────────────────────────────┐
│  阶段二：LLM 清洗与结构化（Python）    │
│  ├─ 调用LLM（DeepSeek/Qwen）逐份清洗  │
│  ├─ 纠正OCR排版错误                   │
│  ├─ 按统一MD模板重组内容              │
│  └─ 输出高质量MD                     │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│  阶段三：父文档切片与索引             │
│  ├─ 文档级 → 章节级 → 条款级 三级切片  │
│  ├─ 建立 parent_document_id 映射      │
│  ├─ FAISS 向量化 + Chroma 元数据存储  │
│  └─ 索引就绪                         │
└─────────────────────────────────────┘
```

### 4.2 文档解析引擎选型（已确认）

| 文档类型 | 引擎 | 原理 | 速度 | 状态 |
|---------|------|------|------|------|
| DOCX | python-docx | 原生文档解析 | 0.2s/份 | ✅ 已验证 |
| 文本型PDF (95%) | OpenDataLoader PDF | Java后端快速提取 | 0.5-4s/份 | ✅ 已验证，93页/3.6s |
| 扫描件PDF (~5%) | pypdfium2 + RapidOCR | 渲染图片→OCR识别 | ~6s/页 | ✅ 已验证，15页/92s |

> ❌ MinerU: HuggingFace gated模型需授权，无法下载
> ❌ Docling: 大PDF/扫描件触发 std::bad_alloc 内存溢出

### 4.3 LLM 平台：SiliconFlow（硅基流动）

**用途**：阶段二 LLM 清洗 + 正式智能体 Agent 的 LLM 调用

**API 基础信息**

| 参数 | 值 |
|------|----|
| API Base URL | `https://api.siliconflow.cn/v1` |
| 默认模型 | `Pro/MiniMaxAI/MiniMax-M2.5` |
| 认证方式 | `Authorization: Bearer <API_KEY>` |
| 协议 | OpenAI 兼容接口（Chat Completions API） |
| 参考文档 | https://docs.siliconflow.cn/cn/faqs/stream-mode |

**环境变量配置**（Key 已写入系统用户环境变量，不在代码中硬编码）

| 变量名 | 说明 | 设置方式 |
|--------|------|---------|
| `SILICONFLOW_API_KEY` | API 密钥 | `[Environment]::SetEnvironmentVariable("SILICONFLOW_API_KEY", "sk-xxx", "User")` |
| `SILICONFLOW_API_BASE` | API 地址 | 默认 `https://api.siliconflow.cn/v1` |
| `SILICONFLOW_MODEL` | 模型名 | 默认 `Pro/MiniMaxAI/MiniMax-M2.5` |

**Python 调用示例**

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://api.siliconflow.cn/v1",
    api_key=os.environ["SILICONFLOW_API_KEY"],
)

response = client.chat.completions.create(
    model="Pro/MiniMaxAI/MiniMax-M2.5",
    messages=[{"role": "user", "content": "..."}],
    stream=False,
)
```

### 4.4 统一 MD 模板

每份清洗后的 MD 文件格式：

```markdown
# 标题

**标准编号：** GB/T XXXXX-XXXX

## 正文

[Docling解析 + LLM清洗后的核心内容，保留原有结构]

## 关键条款

- **条款X.X：** [条款内容]
- **条款X.X：** [条款内容]
```

### 4.5 父文档召回策略

| 层级 | 粒度 | 用途 | 召回策略 |
|------|------|------|---------|
| 文档级 | 整份标准 | 全文档上下文 | 命中子块时回溯父文档 |
| 章节级 | 单个章/节 | 局部上下文 | 默认召回单元 |
| 条款级 | 单个条款 | 精确匹配 | 最优先命中 |

```
用户提问 → 向量检索(FAISS)命中条款级/章节级
    → 通过 parent_document_id 回溯到父文档
    → 将「子块内容 + 父文档摘要 + 相邻章节」拼入 LLM context
    → LLM 生成带引用来源的回答
```

### 5.4 Agent 核心能力（第一版）

1. **等保标准问答** — 用户问"5G核心网等保三级要求是什么"，Agent 回答标准条款和要求
2. **合规要求查询** — 用户问"数据安全法对运营商有什么要求"，Agent 给出法规要点
3. **模型配置** — 用户自填 Base URL / API Key / 模型名，内置 DeepSeek / ModelScope / 硅基流动默认配置

### 5.5 数据流

```
用户输入 → Agent（RAG: 查询内置标准条款库）→ LLM（生成回答）→ SSE 流式输出 → 前端 HTML 渲染
```

## 7. 设计决策记录

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 前端框架 | Next.js / Vite / CRA | Next.js | SSR 支持好，SEO 友好，App Router 便于 API 集成 |
| Agent 框架 | LangChain / 自建 | LangChain | 生态成熟，工具链完整，后续迁移到 Qwen Agent 可参考 |
| LLM 接入 | 固定Key / 用户自配 | 用户自配 | 灵活性高，支持多种国内模型，无需绑定单一供应商 |
| 回复格式 | Markdown / HTML | HTML | 排版更美观，可展示表格/引用/高亮，符合展示需求 |
| 知识库方式 | 内置文件 / RAG管道 | RAG管道 | Docling + LLM清洗 → FAISS + Chroma混合检索，父文档召回，高质量MD |
| 文档预处理 | 直接使用MD / Docling+LLM | Docling+LLM | 原始PDF/DOCX质量参差不齐，需结构化提取后再切片 |
| 检索策略 | 普通切片 / 父文档召回 | 父文档召回 | 运营商标准条款需上下文关联（条款→章节→全文档），父文档回溯保证召回完整性 |
| 向量数据库 | FAISS / Chroma 二选一 | FAISS + Chroma 混合 | FAISS做语义向量检索，Chroma管理元数据+文档关系+过滤 |
| 包管理 | npm / yarn / pnpm | pnpm | Monorepo 管理更高效 |

## 8. 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 标准条款数量（80-100份核心文档） | 知识库构建工作量 | 分批次处理，先完成最高频的30份标准再逐步扩展 |
| LLM API 稳定性 | 用户体验 | 前端 SSE 流式渲染，断线重连提示 |
| 用户 API Key 安全 | 安全风险 | API Key 仅前端内存存储，不持久化 |
| 不同模型回答质量差异 | 回答准确度 | 内置 system prompt 约束安全领域专业回答 |
| 等保3.0可能发布 | 标准过时 | 知识库设计为模块化，支持标准版本更新 |
