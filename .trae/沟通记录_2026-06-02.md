## 对话 028 - 多Staging管道改造（编码完成，待重启）

**时间**：14:30~15:00

### 背景
用户发现当前入库流程虽然是生产者-消费者双线程架构，但实际存在串行瓶颈：
1. **单消费者** — LLM清洗只有一个线程，后面的文件在队列里等
2. **batch满5才索引** — 前4个文件清洗完了干等第5个
3. **queue满了阻塞生产者** — `maxsize=16` 时生产者被迫等待

### 改造方案
将单队列生产者-消费者改为 **3个Staging槽** 的调度器：

```
staging1: [文件1-5] → worker线程1: LLM清洗5个 → 增量索引
staging2: [文件6-10] → worker线程2: LLM清洗5个 → 增量索引
staging3: [文件11-15] → worker线程3: LLM清洗5个 → 增量索引
            ↑
       生产者(OCR)轮询找可用槽
```

### 关键设计
- **3个槽**，每槽容量5个文件
- 每个槽有自己的锁，互不干扰
- 槽满5个自动启动 worker 线程（LLM清洗 + 存.md + 增量索引）
- 不满5个的尾巴在 producer 结束后自动触发（**已覆盖1-4个文件的边界**）
- 增量索引因为有 `_INDEX_LOCK`，最多1路索引同时跑
- 最多 **3路LLM同时清洗**，预计吞吐提升 **2-3倍**

### 边界覆盖
| 场景 | 处理方式 |
|:----|:---------|
| 少于5个文件 | Producer结束 → Tail扫描 → 启动worker处理剩余文件 |
| 恰好5个文件 | 1个槽满 → 直接启动worker |
| 13个文件 | 前10个占2个槽，最后3个占第3个槽，tail起worker |
| 22个文件 | 前15个占满3个槽，第16-20占释放后的槽，最后2个走tail |
| 3个槽全满 | Producer在轮询循环sleep(2)等槽释放 |

### 修改文件
- **main.py** — `_run_processing_task()` 整体改造
  - 删除了旧代码的 `result_queue`、`producer_done`、`new_md_paths` 变量
  - 新增 `_slot_worker()` 处理单个槽的清洗+索引
  - 新增3个 `staging_buffers` + `staging_locks` + `staging_busy`
