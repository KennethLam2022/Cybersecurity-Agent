## 对话 017 - 检索效果验证 + 硅基流动 Reranker

**日期**：2026-05-24

### 内容
编写 `retrieval_test.py` 对向量库进行 18 个覆盖全领域的查询测试，并接入硅基流动 `BAAI/bge-reranker-v2-m3` 做重排序对比。

### 测试结果

| 维度 | FAISS 纯向量 | + Reranker | 变化 |
|------|-------------|-----------|------|
| 查询命中率 | 18/18 (100%) | 18/18 (100%) | — |
| Top-1 分类命中率 | 7/18 (39%) | 9/18 (50%) | +11% |
| Rerank 改变排序 | — | 18/18 (100%) | 每次都调序 |
| 平均耗时 | 0.22s | +1.68s | 总 ~1.9s |

### 观察
- Reranker 每次排序都不同，且得分分布有明显区分（最高 0.99 vs 最低 0.08），说明 cross-encoder 的语义理解比向量检索更深
- Reranker 能更准确定位到具体章节（如直接命中"法律责任"章节而非"总则"）
- 首次 FAISS 检索较慢（~2.6s，Ollama 模型加载），后续稳定在 0.1-0.3s
- Reranker API 稳定在 1.5-2.5s（硅基流动网络延迟）

### 评估结论
- FAISS 检索效果已足够好（100% 召回），Reranker 在排序精度上有可感知的提升
- 综合耗时 ~1.9s，对于非实时场景可以接受
- 冠军方案的 "FAISS + Reranker" 链路验证通过

### 架构
```
query → FAISS (top_k×4) → Reranker (top_k) → 结构化结果
```

### 接口
```python
from retriever import CyberRetriever

retriever = CyberRetriever()
results = retriever.search("等保三级 访问控制要求", top_k=5)
# 返回: [{"content", "file_name", "category", "section",
#          "chunk_id", "parent_id", "faiss_score", "rerank_score"}, ...]
```

## 对话 019 - Chroma workaround + 双库检索

**日期**：2026-05-24

### 内容
1. 确认 ChromaDB #7090 即是我们遇到的 compaction bug（根因：Rust Compactor pickle float/int 序列化不匹配）
2. 验证 workaround：`hnsw:sync_threshold=100000`（设得比总嵌入数大，Compactor 永不运行）→ 写入、重开 client、查询全部通过 ✅
3. 更新 `retriever.py` 支持双库检索（Chroma + FAISS）

### Chroma workaround 验证
```
写入:  7316 chunks ✅（从 FAISS 逆向提取向量，跳过二次 embedding）
重开:  7316 chunks ✅
查询:  3 条结果 ✅
耗时:  ~18s
```

### 双库检索测试（6 个查询）

| 模式 | 结果 | Top-1 分类命中 |
|------|------|---------------|
| faiss+chroma | 9条/查询（FAISS先填充，Chroma去重覆盖） | 3/6 |
| faiss 单独 | 6/6 ✅ | 3/6 |
| chroma 单独 | 6/6 ✅ | 3/6 |

**结论**：两个数据库各自独立可用，互备冗余。数据源相同、embedding 相同，排序结果基本一致。双库模式实际起冗余备份作用。

### 当前架构
```
query
├── FAISS 召回 (top_k×3) ──┐
├── Chroma 召回 (top_k×3) ──┼── 去重合并 ── Reranker ── top_k 结果
                           └── 冗余备份
```
