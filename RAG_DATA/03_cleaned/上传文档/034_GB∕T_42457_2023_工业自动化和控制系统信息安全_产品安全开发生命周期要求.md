# 引言

IEC 62443是应用于工业自动化和控制系统安全的系列国际标准。目前我国已采用该系列标准发布了GB/T 33007—2016《工业通信网络 网络和系统安全 建立工业自动化和控制系统安全程序》（IEC 62443-2-1:2010，IDT）、GB/T 35673—2017《工业通信网络 网络和系统安全 系统安全要求和安全等级》（IEC 62443-3-3:2013，IDT）、GB/T 40211—2021《工业通信网络 网络和系统安全 术语、概述和模型》（IEC 62443-1-1:2009，IDT）、GB/T 40218—2021《工业通信网络 网络和系统安全 工业自动化和控制系统信息安全技术》（IEC/TR 62443-3-1:2009，IDT）、GB/T 40682—2021《工业自动化和控制系统网络安全 第2-4部分：IACS服务提供商的安全程序要求》（IEC 62443-2-4:2015，IDT）和本文件。这些标准共同构成应用于工业自动化和控制系统安全的系列国家标准。

本文件是解决工业自动化和控制系统（IACS）安全问题的系列标准的一部分。本文件介绍工业自动化和控制系统环境中使用的产品的信息安全相关开发生命周期要求，并就如何满足每个要素描述的要求提供指导。

本文件大部分来自ISA安全合规研究所（ISCI）的安全开发生命周期评估（SDLA）认证要求[26]。SDLA程序基于以下来源：
- ISO/IEC 15408-3（通用标准）[18]；
- 开放式Web应用程序安全项目（OWASP），全面轻量级应用程序安全性过程（CLASP）[36]；
- 迈克尔·霍华德和史蒂夫·利普纳[43]的安全开发生命周期；
- IEC 61508 电气/电子/可编程电子的安全相关系统的功能安全[24]；和
- RCTA DO-178B 机载系统和设备认证中的软件考虑[28]。

因此，所有这些都可以被认为是本文件的来源。

本文件包含的信息安全要求，可以作为任何自动化和控制产品的开发人员考虑信息安全问题时的指导。

# 工业自动化和控制系统信息安全 产品安全开发生命周期要求

## 1 范围

本文件规定了用于工业自动化和控制系统产品的信息安全开发的过程要求。它定义了一个用于开发（包括编码准则）、验证和确认、缺陷管理、补丁管理和产品退役。这些需求可以应用于新的或现有的过程，以开发、维护和淘汰新的或现有的产品硬件、软件或固件。这些需求适用于产品的开发人员和维护人员，但不适用于产品的集成人员或用户。本文件的需求摘要清单见附录B。

## 3 术语、定义、缩略语和惯例

ISO和IEC的术语数据库可以通过下述网址访问：

- ISO：http://www.iso.org/obp。

### 3.1 术语和定义

IEC TR 62443-1-2界定的以及下列术语和定义适用于本文件。

#### 3.1.1 滥用用例 abuse case
用于执行负面操作的测试用例。
注：滥用用例测试通常是基于威胁模型的模拟攻击。滥用用例是一个系统与一个或多个行动者之间完全相互作用的一种类型，其中交互的结果是故意地对系统、行为者之一或系统中的一个利益相关者有害。

#### 3.1.2 访问控制 <保护> access control <protection>
保护系统资源免受未经授权的访问。

#### 3.1.3 访问控制 <过程> access control <process>
根据安全策略对系统资源的使用进行管理的过程，并且只有符合该策略的授权用户才被允许。
注：访问控制包括IEC 62443系列其他部分规定的标识和鉴别需求。

#### 3.1.4 管理员 administrator
被授权管理产品或系统的安全策略/功能的用户。

#### 3.1.5 资产 asset
物理的或逻辑的对象，由组织拥有或者在组织的监管之下，对组织有可预见的价值或实际价值。
注：在这种特定情况下，资产是IACS的一部分。

#### 3.1.6 资产所有者 asset owner
对一个或多个IACS负责的个人或组织。

#### 3.1.7 攻击面 attack surface
可能被攻击者利用的，可被访问的系统物理和功能接口。

#### 3.1.8 审计日志 audit log
需要比典型事件日志提供更高级别的完整性保护的事件日志。
注：审计日志可用于防止否认对某行为的责任。

#### 3.1.9 鉴别 authentication
为一个实体声称的特征是正确的而提供的保障措施。
注1：并非所有用于认证身份的凭证都是平等创建的。凭证的可信度由配置的认证机制确定。硬件或基于软件的机制可以强制用户在访问设备数据之前证明自己的身份。典型的例子就是通常通过身份提供者证明用户身份。
注2：鉴别包括验证人员用户，以及非人员用户如设备或过程。

#### 3.1.10 自动化解决方案 automation solution
控制系统和任何已经安装和配置在IACS中运行的补充硬件和软件组件。
注1：自动化解决方案在IEC 62443系列的这一部分中被用作专有名词。如不做说明，本文件的“安全”都是指“信息安全”。
注2：自动化解决方案通常由系统集成商创建，他们通过选择、采购和集成组件（例如，工作站、控制器和设备），然后实施。由此产生的配置被称为自动化解决方案。
注3：自动化解决方案可由多个供应商的组件组成，包括控制系统的产品供应商。

#### 3.1.11 禁用功能 banned function
因为存在误用倾向较小、更安全的版本，而不再推荐使用的软件方法。
注：禁用功能有时被称为禁用方法或禁用应用程序编程接口（API）。

#### 3.1.12 最佳实践 best practice
供应商已确定的用于安全设计、开发、测试、维护或废弃产品的准则，通常由安全和工业自动化领域共同推荐。
示例：最小特权、经济机制（economy of mechanism）和最少公共机制。

#### 3.1.13 组件 component
构成产品或系统的部件之一。
注：组件可以是硬件或软件，可以细分为其他组件。

#### 3.1.14 配置管理 configuration management
用以识别一个进化的系统组件的原则，以控制这些组件的变化并保持整个生命周期的连续性和可追溯性。

#### 3.1.15 纵深防御 defense in depth
使用几个独立方法来防护系统，以抵御任何特定攻击的方式。
注：纵深防御意味着多层的安全和检测，即使在单个系统上，并提供以下功能：
- 基于任何单层保护都有可能会被攻破的理念；
- 攻击者可能突破或绕过每一层而不被发现；
- 某一层的缺陷可以通过其他层的能力来缓解；
- 系统安全成为整体网络安全的一个安全层集合；
- 每层宜是自治的，不依赖于相同的功能，也不具有与其他层相同的失效模式。

#### 3.1.16 依赖组件 dependent component
产品所依赖的外部组件。
示例：Java运行时环境或驱动。
注：包括硬件和软件。

#### 3.1.17 不宜用功能 deprecated function
支持但不再推荐使用的软件方法。
注：在即将过时（已从供应商提供的功能集中删除）之前，方法通常不推荐使用。不宜用功能有时称为不宜用方法或不宜用API。

#### 3.1.18 外部提供的组件 externally provided component
组件包含在由外部组织开发的产品中，而不是专门为一个供应商开发。
注：例如购买的软件和开源软件。

#### 3.1.19 模糊测试 fuzz testing
针对测试对象创建格式错误、非预期的数据或调用序列，并验证它们能够被恰当处理的过程。

#### 3.1.20 工业自动化和控制系统 industrial automation and control system
用于控制工业生产过程的系统，包括相关的设备、网络和软件，用于自动化操作。
注1：IACS可以包含未安装在资产所有者现场的组件。
注2：IACS的定义取自IEC 64333-3-3[10]并在图2中示出。

#### 3.1.21 补丁管理 patch management
涉及获取、测试和安装软件补丁（代码更改）到产品的系统管理领域。
注1：有关更多信息，请参阅IEC TR 62443-2-3[7]。
注2：补丁管理也适用于在发布产品之前对所包含第三方库更新的过程。

#### 3.1.22 产品 product
为其他产品的使用所制造、开发或改进的系统、子系统或组件。
注：本文件中定义的实践所需的过程反复应用于产品设计的所有级别（例如，从系统级到组件级）。

#### 3.1.23 产品安全上下文 product security context
由产品的预期使用环境（资产所有者部署）提供给产品的安全性。
注：通过其预期的环境向产品提供的安全性可以有效地限制适用于产品的威胁。

#### 3.1.24 产品供应商 product supplier
硬件和/或软件产品的制造商。
注：产品供应商包括负责开发和维护产品的实体，不仅仅包括制造商（例如集成商）。

#### 3.1.25 产品用户 product users
硬件和/或软件产品的用户，包括资产所有者、集成商和维护人员、重新使用或包含此产品的其他组件或产品的供货商。

#### 3.1.26 记录 record
说明取得的成果或提供进行活动的证据的文件。

#### 3.1.27 退化 regression
系统组件变更所引起的功能性、可靠性或操作的不利影响，或引入了额外的缺陷。

#### 3.1.28 根因 root cause
启动导致输出结果或影响利益的条件或因果链的最初原因。
注：这些弱点通常是由于滥用最佳实践造成的。

#### 3.1.29 安全性缺陷 security defect
可被利用来破坏资产或资源的设计或实施上的不足。

#### 3.1.30 安全顾问 security advisor
指导团队在SDL（安全开发生命周期）过程中活动的组织角色。
注：安全顾问可以是项目团队的一员，也可以是团队顾问，在需要时提供指导和协助。

#### 3.1.31 安全事件 security incident
对资产所有者造成一定影响的安全破坏，或者对系统安全破坏的失败尝试，失败尝试的结果可能对资产所有者具有一定的影响意义。
注：术语“擦肩而过”通常用来描述一个事件，该事件在稍有不同的环境下有可能发展成一个事故。

#### 3.1.32 安全相关事件 security-related issue
潜在地会影响产品安全性的产品设计或实施的特性特点。

#### 3.1.33 安全验证和确认测试 security verification and validation testing
执行测试以评估组件、产品或系统在用于其预期的产品安全上下文时的总体安全性，并确定是否组件、产品或系统是否满足产品安全需求并满足其设计的安全目的。
注：安全验证测试通过针对产品安全上下文和纵深防御策略开展的其他测试来对确认安全有效测试进行补充。

#### 3.1.34 系统集成商 system integrator
专门将组件子系统组合成一个整体，并确保这些子系统按照项目规范执行的人员或公司。

#### 3.1.35 第三方供应商 third party supplier
独立于产品供应商组织之外的组织。

#### 3.1.36 威胁 threat
可能通过非授权访问、破坏、披露、数据修改和/或拒绝服务方式，对运营（包括任务、功能、形象或者名誉）、资产、控制系统或者个人具有不利影响的环境或者事件。

#### 3.1.37 威胁建模 threat modelling
识别潜在的信息安全问题的安全性设计分析技术。
注：威胁建模通常与攻击树是同义词，当这些问题可以相对容易且经济高效地解决时，软件和硬件架构师使用这些模型来及早识别和缓解潜在的安全问题。

#### 3.1.38 信任边界 trust boundary
威胁模型的元素，描述一个需要身份验证或者发生信任级别变化（从高到低或反之亦然）时的边界。
注1：产品用户的信任边界执行机制通常包括身份验证（例如，质询/响应、密码、生物识别或数字签名）和相关授权（例如访问控制规则）。

#### 3.1.39 单元测试 unit testing
验证一个单独的计算机软件或硬件单元是否按预期运行。
注1：自动验证或测试通常由计算机测试软件执行。
注2：什么是源代码单元是设计决策问题。单元通常被设计为应用程序中最小的可测试部分，它可能包括一个或多个计算机程序模块，也可能包括相关的控制数据、使用过程和操作过程。在程序编程中，一个单元可以是一个完整的模块，但更常见的是一个单独的函数或子程序。在面向对象编程中，一个单元通常是一个完整的接口，比如一个类，但可能是一个单独的方法。

#### 3.1.40 用户 user
以授权或未授权的方式访问系统的人员、组织实体或自动化过程。

#### 3.1.41 区域 zone
基于功能、逻辑和物理（包括位置）关系，描述目标系统（SuC）分区的实体集合。
注：区域通常基于共性安全需求，关键性（例如高价值、健康、安全（safety）或环境影响）、功能性、逻辑或物理（包括位置）关系。

## 4 通用原则

### 4.1 概念

这些需求的主要目标是提供通过采用安全的设计和纵深防御方法的框架，实现对工业自动化和控制产品、系统中使用的产品的设计、制造、维护和退役。该框架的应用旨在确保组件、产品或系统在整个生命周期内具有与其预期风险等级相称的安全性。尽管本文件中未讨论信息安全等级的概念，但遵守本文件将有助于确保产品中实施的安全功能（见IEC 62443-4-2[11]）得到正确实施，并确保已知的任何安全脆弱性在产品中被消除或缓解。因此，遵守本文件有助于使产品满足整体能力安全等级（SL-C）的需求。

这些需求的第二个目标是使开发过程与工业自动化和控制系统产品用户（例如，IEC 62443-2-4能力的提供者，如集成商和运维服务商）的安全需求提升相匹配。这意味着该过程需要生成诸如良好文档化的安全性配置管理、补丁管理策略和规程等，并提供关于产品中发现的安全脆弱性的简洁明了的沟通。

注：对于IACS，IEC 62443-3-2[9]描述了确定与系统区域和管道相关的预期风险等级的需求。

### 4.2 成熟度模型

产品供应商有多种方法可以满足本文件规定的需求。成熟度模型设定了满足这些需求的基准。这些基准由成熟度等级定义，见表1。成熟度等级基于能力成熟度模型集成（CMMI）开发（CMMI-DEV）模型[42]。表1在描述列中显示了与CMMI-DEV的关系。

成熟度等级提供了供应商如何彻底满足这些需求的更多细节。因此，系统集成商和资产所有者可以使用这些等级来评估开发产品的严格程度。

本条描述成熟度等级的目的是为组织提供基准，以确定他们准备使用的过程和规程来设计和实施产品安全。使用这些基准，组织可能会发现其尚未准备好将所有需求落实到相同的成熟度等级。

## 5 实践1—安全管理

### 5.1 目的

安全管理实践的目的是确保安全相关的活动在整个产品的生命周期都得到充分的计划、文档化和执行。

如果对安全相关活动的计划和支持不够重视，同时由于资源不足、时间不足或过程效率低下的影响，活动可能会变得无效。同样，产品安全要求与配置管理，信息技术策略和规程以及供应链管理等相关组织过程的不一致也会危及安全产品开发生命周期的有效性。

### 5.2 SM-1：开发过程

#### 5.2.1 需求

常规产品开发/维护/支持过程应文档化并被以与一般公认的产品开发过程保持一致并整合的方式执行，包括但不限于：
a) 使用变更控制和审计记录进行配置管理；
b) 产品描述和需求定义，且需求具有可追溯性；
c) 软件或硬件设计和实施实践，如模块化设计；
d) 可重复的测试验证和确认过程；
e) 审查和批准所有开发过程记录；
f) 生命周期支持。

### 5.3 原由和附加指南

这个过程需要确保产品供应商已完好地定义和证明产品开发过程可以扩展到支持本文件规定的需求。本文件规定的所需过程假定存在成熟的产品开发生命周期。如果没有这些过程或过程没有发挥作用，安全的产品开发生命周期就无法奏效。普遍接受的产品开发过程的例子包括ISO 9001[13]和ISO/IEC 27034[34]合规过程。

该过程是指产品供应商在产品开发生命周期使用的技术，至少支持配置管理、需求定义、设计、实现和测试。

#### 5.4.1 需求
